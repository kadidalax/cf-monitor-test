## 二、控制变量实验：是「操作」，不是「挂着」

4 个阶段各 5 分钟，间隔 2 分钟洗脱，单变量改变：

| 阶段 | viewer | 操作 | Worker 请求 | DO 请求 | DO 时长 |
|------|--------|------|------------|---------|--------|
| A 基线 | ✗ | ✗ | 2 | 0 | 0.4 GB-s |
| **B 只挂后台** | ✓ | **✗** | **+1** | **+2** | **+0.0** |
| **C 只操作** | **✗** | ✓ 36 次 | **+34** | **+19** | **+0.0** |
| D 两者 | ✓ | ✓ 36 次 | +31 | +20 | +0.0 |

外推每小时：

```
只挂后台:  Worker    36/h    DO    24/h
只做操作:  Worker   417/h    DO   220/h      ← 11.6 倍
```

**当时的结论：操作是主因（11.6×），挂在后台几乎免费。**

> ⚠️ **该结论不成立 —— 实验设计有缺陷。**
> 四个阶段全程 WebSocket 都是正常的，因此只测到了状态空间的一半。
> `livePolling.ts:61` 的 `hidden` 守卫是死代码，**WS 一旦坏掉，
> 挂在后台会以 ~510 请求/小时 持续消耗**（重连循环 480 + idle 轮询 30），
> 与 07-30 观测到的 413–575/小时 平台吻合。
> **用户"挂后台烧配额"的原始判断是对的。** 详见方案文档第一节。

### 为什么「挂着」不贵——尽管事件很多

B 阶段 5 分钟内收到 **145 条** WebSocket 消息（agent 从 120s 切到 3s 是真的），
但计费只 +2。原因在官方定价文档：

> "There is no charge for **outgoing** WebSocket messages... For compute requests
> billing-only, a **20:1 ratio** is applied to incoming WebSocket messages."

145 ÷ 20 ≈ 7，与实测 +2 同量级。**事件密度 ≠ 计费量。**

## 三、为什么图表上「肉眼可见」

这不是错觉，两者都真实：

| 日期 | Worker req | 相对基线 |
|------|-----------|---------|
| 07-31 | 767 | 基线 |
| 07-30 | **3,645** | **4.75×** |

活跃使用后台约 **417 请求/小时**，而整站**空闲一整天**才 ~700 请求。
所以用后台一小时 ≈ 半天的空闲基线量，日线图上就是一根明显的柱子。

**图表跳变是真的，配额风险不存在。** CF 控制台 Y 轴自动缩放放大了观感。

> ⚠️ **归因已修正。** 上表的 3,645/天 曾被归因于"活跃使用后台"，
> 但该日的每小时曲线是**持续 7 小时的平直平台（413–575/h）**，
> 而非操作应有的尖峰形态。连续操作 7 小时不现实。
> 更可能是 WS 坏掉后的重连循环（推算 480/h）。
> 两者数值接近（417 vs 480），单凭聚合数据无法判定，**形态是主要判据**。

## 四、错误结论存档（供追溯，勿采信）

### ✗ 错误 1：「DO 永不休眠 → 10,800 GB-s/天 → 占 83% 额度」

误读了这句：

> "Durable Objects that are idle and **eligible** for hibernation are not billed
> for duration, **even before the runtime has hibernated them**."

**「符合休眠条件」即不计费**，无需真正进入休眠状态。文档里的 10 秒只是运行时
**实际回收内存**的时刻，不是计费分界线。消息间隔 0.3 秒完全无妨——两次消息之间
DO 处于「空闲且符合条件」，不计费。只有实际执行 JS 的时间才计费。

实测四阶段 duration 恒为 0.2–0.4 GB-s/5min，**与 viewer 在否无关**，印证之。

### ✗ 错误 2：「挂在后台是主因，40 倍放大」

事件密度确实 40×（2 次/分 → 80 次/分），但因 20:1 折算，计费增量仅 +2。
控制变量实验直接推翻。

### ✗ 错误 3：「Notifications 页面加载触发 18 个 API 调用」

那是全文件 `apiFetch` 出现次数，含写操作 handler。实际 `loadActiveTab`
**只加载当前 tab**，挂载成本 1–2 个请求。同理 `Websites` 的 `loadChecks`
只在编辑单个监控项时触发，非每项扇出。

## 五、仍然成立的发现

1. **容量估算器结构性错误**（`admin.ts:1150`）
   ```js
   const estimatedWorkerRequestsPerDay =
     agentPingTaskPullsPerDay +      // WS 消息，不是 Worker 请求
     pingResultReportsPerDay +       // WS 消息，不是 Worker 请求
     agentBasicInfoReportsPerDay +   // WS 消息，不是 Worker 请求
     agentWebsocketConnectsPerDay;
   ```
   把 WS 消息当 Worker 请求计入，同时**完全漏掉浏览器侧和 cron**。
   面板显示 5,956/天，实测 1,474/天。**这是双方误判的根源。**

2. **viewer token TTL=121s 导致强制断连**（`live-data.ts:1127`）
   ```js
   session.send({type:'viewer_expired'}); session.close(1000, 'Viewer live window expired');
   ```
   每个标签页每 2 分钟被强制断开重连一次。**这是体验缺陷**，成本影响很小。

3. **viewer token 严格绑定 IP**（`viewer-token.ts:116`）
   双栈 / VPN / CGNAT 下 token IP ≠ WS IP → 403 → 降级为 HTTP 轮询。

4. **降级路径缺少退避**（`LiveDataContext.tsx`）
   `scroll` 监听触发轮询、`error` 与 `close` 重复 `fetchLiveData()`、
   重连固定 30s 无退避。属于尾部风险保险丝。

## 六、结论（第二轮修订）

- **不存在配额危机**，各项指标占用 1%–4%。这条仍然成立。
- **07-30 的跳变归因需要修正。** 当时归因于"后台操作"（实测 417 req/h），
  但 WS 坏掉时的重连循环推算为 480 req/h —— **两者数值太接近，
  单凭每小时聚合数据无法区分**。
  倾向于后者的理由：该平台**持续了 7 小时**，连续点击 7 小时不现实，
  而无人值守的重连循环正好会呈现这种平直形态。
- 真正的缺陷是**放大器**：`livePolling.ts` 中死掉的 `hidden` 守卫、
  固定 30 秒无退避的重连、以及整条失效的会话过期链。
  它们把任意一次 WS 失败放大成无上限的请求循环，**对触发原因免疫**。
- **不应**为此牺牲 3 秒实时性——它不是成本来源。这条仍然成立。
- **教训**：控制变量实验只有在覆盖完整状态空间时才有说服力。
  本次实验漏掉了"故障态"这一维，导致结论方向性错误。
